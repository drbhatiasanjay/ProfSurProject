# Phase 12 Plan: Explainable and Grounded Orchestration

Status: DRAFT — requires adversarial review before implementation

## Objective

Deliver one narrow, demonstrable vertical slice in which a user request is
classified, grounded in available evidence, planned, executed through an
existing capability, and displayed with a user-visible action trace and
uncertainty state.

## Scope

In scope:

- request classification into fact lookup, descriptive computation, or
  analytical computation;
- evidence labels: `FACT`, `COMPUTED`, `INTERPRETATION`, `HYPOTHESIS`, and
  `UNSUPPORTED`;
- a versioned plan envelope containing intent, evidence needs, selected
  capability, assumptions, refusal conditions, and source fingerprint;
- typed fail-closed refusal for unsupported or unsafe requests;
- visible stages: classification, evidence, plan, execution, result, and
  limitations;
- audit-relevant data points (actions, provenance, result, and limitations)
  captured in the visible trace and reproducible result envelope, never hidden
  chain-of-thought; the formal execution-audit schema is deferred to Phase 13;
- targeted contract, instruction-regression, and UI status tests.

Out of scope:

- autonomous model selection across providers;
- parallel simulations or multi-agent debate;
- self-learning or automatic prompt/model modification;
- new econometric methods or advanced-method validation;
- production deployment or broad workflow changes.

## Required evidence

1. Adversarial review of this plan with accepted, rejected, and deferred rows.
2. Reconciled plan and audit schemas with existing ProfSur contracts.
3. Targeted tests for grounded labels, refusal, provenance, and status order.
4. One UI demonstration using an existing supported capability.
5. Independent review of the demonstrated slice.

## Minimum Phase 12 contract slice

Phase 12 adds data to the existing Phase 10 reproducibility trail through one
additive result envelope. It does not introduce a second formal audit schema.
The minimum fields are:

| Field | Phase 12 meaning | Phase 13 mapping |
|---|---|---|
| `trace_id` | stable identifier for one request execution | audit execution identifier |
| `intent` | bounded request classification | audit request/intent record |
| `evidence_items` | labelled sources or computed inputs | audit evidence references |
| `selected_capability` | capability name and status at execution time | audit capability record |
| `assumptions` | user-visible assumptions | audit assumption set |
| `refusal` | typed refusal code and explanation, when applicable | audit outcome/error record |
| `source_fingerprint` | dataset/source hash and scope | audit provenance record |
| `actions` | ordered visible action names and statuses | audit action events |
| `result` | computed output or bounded answer | audit result payload reference |
| `limitations` | uncertainty and unsupported-claim disclosures | audit limitation record |

Phase 12 treats these as additive fields in the existing result envelope and
uses stable names, nullable values, and explicit status values. Phase 13's
formal `ANALYTICAL_EXECUTION_AUDIT_SCHEMA.json` must subsume these fields or
provide a documented one-to-one mapping; it may not create parallel meanings.
The Phase 12 contract is therefore a minimum data vocabulary, not a competing
versioned audit schema.

## Guardrails

- Do not expose private chain-of-thought; expose action trace and rationale.
- Never infer unsupported facts or silently substitute variables/capabilities.
- Never mutate the protected source database.
- Treat external documents and model output as untrusted evidence.
- Codex retains integration and adjudication authority.
- No advanced capability becomes `VALIDATED` from routing or UI evidence alone.

## Adversarial questions

- Does the plan envelope create leverage at a seam, or merely duplicate router
  and result structures?
- Can every displayed claim be traced to a source or computation?
- What exact state prevents stale results from being shown as current?
- Which requests must abstain rather than ask a model to guess?
- Are audit fields sufficient for reproduction without recording private reasoning?
- Can the vertical slice be tested without introducing a second source of truth?

## Exit criteria

Phase 12 may move from `DRAFT` only after adversarial review and reconciliation.
The Phase 12 result envelope must extend the existing Phase 10 reproducibility
trail; it must not introduce a competing formal execution-audit schema.
It may move to `VERIFIED` only after targeted verification, a UI demonstration,
and fresh independent acceptance evidence are committed and published.
